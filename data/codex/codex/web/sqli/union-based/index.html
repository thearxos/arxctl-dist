UNION-based SQLi

Extracting data via UNION SELECT when query results are reflected in the response.

Common failure modes

  • No output despite no error - the application takes only the first row. Add ORDER BY id DESC LIMIT 1 OFFSET <N> (MySQL) to access other rows, or use a payload that forces your row to be first.
  • UNION keyword filtered - try UnIoN, /*!UNION*/ (MySQL), UNION ALL. See Filter bypasses.
  • Errors visible but no UNION result - the app catches errors and shows them but doesn't render row data. Use error-based extraction below.
  • Stacked queries blocked but you need them - UNION cannot run INSERT/UPDATE/DELETE or stored procedures. For destructive queries you need stacked query support (MSSQL, PostgreSQL).

Next move

  • Got data back via UNION → escalate scope: dump all tables (information_schema.tables), then dump rows from interesting tables - start with users, admin, credentials, anything ending in _keys or _secrets
  • UNION keyword filtered → try UnIoN, /*!UNION*/, or fall back to Bypasses for case/comment variants
  • Column count probes returning errors instead of difference → switch to error-based extraction - useful when ORDER BY/UNION SELECT are blocked but error reflection works
  • No output reflected in response → not actually UNION-viable; move to Boolean blind or Time-based blind
  • Got DB credentials from a dumped users table → try them against the application login, SSH, MSSQL/MySQL native ports (MSSQL), and any other services on the host
  • MSSQL backend with admin creds → xp_cmdshell for RCE
  • File-read primitive available (LOAD_FILE / pg_read_file) → File operations - extract /etc/passwd, app configs, SSH keys
