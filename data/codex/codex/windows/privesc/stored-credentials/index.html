Stored Credentials

Extracting secrets that applications and Windows itself hold on a host - Windows Credential Manager (cmdkey plus runas /savecred), saved browser logins via SharpChrome/DPAPI, KeePass databases cracked offline with keepass2john and Hashcat, cleartext passwords in the registry (AutoLogon, PuTTY proxy), saved wireless keys, and the catch-all sweeps with LaZagne and SessionGopher. Reuse what you recover for a higher-privileged local or domain account.

MITRE T1552, T1078, T1552.001D3FEND D3-CH, D3-FAIMPACT CredentialTheft, PrivEsc

TL;DR

Beyond loose files (credential hunting), applications and Windows itself keep secrets in structured stores - the Credential Manager, browser login databases, password managers, the registry, the wireless profile store. Some you can decrypt in your current user context (DPAPI does the work for you); some you crack offline; some you just use without ever seeing the plaintext. Any recovered secret is a candidate for reuse against a higher-privileged local or domain account.

Success indicator: a cleartext credential (or a cracked password / usable saved session) that authenticates as a different, more-privileged principal - verified with runas, RDP, WinRM, or the target service.

Windows Credential Manager (cmdkey / runas)

cmdkey lists credentials the user saved for other hosts - RDP targets, network shares, generic app logins. These are DPAPI-protected, so you don't get the plaintext from cmdkey, but you can use them:

Mind the entry type - it determines what you can do with it:

  • A LegacyGeneric:target=TERMSRV/<host> entry is scoped to the RDP client (mstsc): connecting to that host auto-authenticates as the stored user. It is not an interactive-logon credential, so runas /savecred will not use it (that command still prompts for the password).
  • A Domain:interactive=<DOMAIN>\<user> entry is the one runas /savecred looks up. When such an entry exists, you can reuse the saved secret to run anything as that user, no password needed:

So cmdkey /list showing only a TERMSRV/... entry buys you an RDP session as that user, not a runas shell - check which type you actually have.

To recover the actual plaintext (to reuse elsewhere), you need the user's DPAPI context - mimikatz dpapi::cred / sekurlsa::dpapi, or SharpDPAPI, as that user or as SYSTEM.

Saved browser logins

Browsers have historically stored site logins encrypted with DPAPI (and, in later Chrome, an AES state key that is itself DPAPI-wrapped) - so a process running as the logged-in user could decrypt them. SharpChrome (part of SharpDPAPI) handles the state-key unwrap and prints cleartext:

cookies /unprotect similarly dumps session cookies (useful for session hijacking where the password has MFA).

Caution

App-Bound Encryption breaks the simple path on current Chrome. From Chrome 127 (2024) on supported Windows, cookies - and increasingly logins - are protected by App-Bound Encryption (ABE), which deliberately stops another process running as the same user from decrypting them through ordinary DPAPI. So the /unprotect flow above reliably recovers only legacy DPAPI-backed stores (older profiles, older Chromium builds, and some non-Chrome Chromium browsers); against a current Chrome profile you need ABE-aware tooling or to run in the browser's own context. Decrypting these stores is also not silent (it touches the DPAPI masterkey and the login DB), but see the detection note below - don't rely on a fixed list of event IDs.

Password managers (KeePass, offline cracking)

Enterprise password managers - KeePass, 1Password, Thycotic, CyberArk - are high-value: a single vault, especially an IT or departmental one, can hand you admin over servers, network gear, and databases. KeePass stores its vault locally as a .kdbx file protected by a master password; find one on a host or share and you can crack it offline.

Open the vault with the cracked master password to recover everything inside. (A .kdbx protected additionally by a key file can't be cracked with the password alone - you need that file too; hunt for the .key/.keyx alongside it.)

Cleartext passwords in the registry

Some Windows features and apps write passwords to the registry in cleartext. LaZagne finds these, but enumerate manually too.

Windows AutoLogon

AutoLogon stores the auto-logon account's password in plaintext under a key standard users can read:

AutoAdminLogon = 1 with a DefaultPassword present is the win. (Sysinternals Autologon.exe stores the password as an LSA secret instead of cleartext - so a host configured that way shows no DefaultPassword here, and the secret must be pulled from LSA.)

Catch-all tool sweeps

When the targeted checks don't land, the broad tools sweep dozens of applications at once.

  • LaZagne - lazagne.exe all pulls stored credentials from browsers, mail clients, databases, sysadmin tools, wifi, and Windows stores (Credman, DPAPI, LSA secrets, AutoLogon). Scope to a module (lazagne.exe browsers) to stay quieter. Output to text or JSON.
  • SessionGopher - Invoke-SessionGopher reads remote-access session data from the registry, but mind what it actually recovers: it decrypts saved passwords for WinSCP, FileZilla, and SuperPuTTY, whereas for PuTTY and RDP it returns only session metadata (host, and for RDP a username hint) - PuTTY doesn't store a password to recover. It reads the HKEY_USERS hives currently loaded, so as your own user it sees your sessions and as local admin it covers the profiles loaded at that moment, not every account that has ever logged on - a clean result isn't proof there are no saved sessions. Can also crawl drives for .ppk, .rdp, and .sdtid files.
  • MailSniper - on a domain-joined host with the user's Exchange mailbox, searches their email for "pass", "cred", etc. Mail is an underrated credential store.

Note

These tools are heavily signatured - rename, recompile, or fall back to the manual registry/file techniques above when AV/EDR detection is a concern. LaZagne in particular touches many sensitive stores and is loud.

Defense

  • Prefer Windows Hello for Business / managed identities over saved passwords; where Credential Manager is used, accept that any process as that user can reuse the entries.
  • Never enable AutoLogon with a cleartext DefaultPassword; if auto-logon is unavoidable, use Sysinternals Autologon.exe (LSA secret) and restrict the account's rights.
  • Protect KeePass vaults with a key file and a strong master password, and keep .kdbx files off shared/world-readable locations where they can be exfiltrated and cracked offline.
  • Enforce strong wireless PSKs or move to 802.1X so a recovered key isn't a standing network credential.
  • Credential-store access leaves telemetry only if you configure it: enable process-creation auditing with command line (Event ID 4688) to catch SharpChrome/LaZagne/SessionGopher invocations, enable the Microsoft-Windows-Crypto-DPAPI/Debug channel (Event ID 16385) for DPAPI masterkey use, and put a SACL on the browser Login Data/Local State files for object-access events. Treat these as signals to correlate - process creation near a DPAPI masterkey read near a login-DB open - not as standalone proof, and don't look for Event ID 4983 here (that's an IPsec negotiation failure, unrelated to credential access).
