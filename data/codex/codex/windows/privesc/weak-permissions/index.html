Weak Service & Registry Permissions

Escalating to SYSTEM through misconfigured ACLs - a modifiable service binary you can overwrite, a service whose configuration you can rewrite (sc config binPath), a writable services registry key (ImagePath), unquoted service paths, and modifiable autorun entries. Enumerate with SharpUp/PowerUp/winPEAS/accesschk, then turn a weak permission into a SYSTEM shell or a new local admin.

MITRE T1543.003, T1574, T1068D3FEND D3-FAIMPACT PrivEsc, SystemCompromise

TL;DR

Most Windows services run as NT AUTHORITY\SYSTEM. If an unprivileged user can modify what a service runs - its binary on disk, its configuration, or its registry key - starting (or waiting for) that service runs attacker code as SYSTEM. These flaws are rare in large-vendor software but common in third-party, open-source, and in-house applications.

Success indicator: the service's next start runs your command as SYSTEM - a new local admin appears in net localgroup administrators, or a reverse shell returns nt authority\system.

Enumerate the weakness

Automated scanners find these fastest; each flags a slightly different subset, so run more than one when a target is quiet:

  • SharpUp (audit) - Modifiable Services (config ACL) and Modifiable Service Binaries (file ACL).
  • PowerUp.ps1 (Invoke-AllChecks) - the PowerShell equivalent; also finds unquoted paths and AlwaysInstallElevated.
  • winPEAS (servicesinfo) - broad, noisy, colour-coded.
  • accesschk.exe (Sysinternals) - the manual verifier for a specific service or the whole services registry tree.

Then confirm by hand before acting - the exploit path differs by which permission is weak.

Escape the quotes (\"..\") so they're literally stored in ImagePath.

5. Modifiable autorun binary

Programs set to run at logon/boot are another path - if you can overwrite a listed binary or write to its Run key, you execute as whoever logs in next (an admin, ideally):

Check write access to each listed command and to the backing HKLM\...\CurrentVersion\Run keys. This is slower-yielding than the service paths above (it waits on a logon) but is a reliable persistence-plus-escalation primitive when a privileged user logs in regularly.

Defense

  • Service binaries and their directories should be writable only by Administrators/SYSTEM; audit third-party installers, which frequently loosen these ACLs.
  • Lock down service object permissions - unprivileged groups should never hold SERVICE_CHANGE_CONFIG or write to a service's registry key.
  • Always quote service binary paths. Installers should wrap BINARY_PATH_NAME in quotes.
  • Run services with the least privilege they need (a virtual/service account, gMSA) rather than LocalSystem, so a hijack yields less.
  • Baseline autorun entries and alert on changes to Run keys and startup folders.
