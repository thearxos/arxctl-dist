Credential Hunting

Finding credentials at rest on a Windows host - cleartext config files (web.config, unattend.xml), PowerShell history and DPAPI-protected PowerShell credentials, browser dictionary files, Sticky Notes databases, and the classic file-system and share sweeps with findstr, Get-ChildItem, and Snaffler. The lowest-value, highest-effort escalation lookup - run it when token, group, and misconfiguration checks come up empty, and again after every context change.

MITRE T1552.001, T1552, T1078D3FEND D3-FA, D3-CHIMPACT CredentialTheft, PrivEsc

TL;DR

When the privilege/token/group/ACL checks don't produce a primitive, hunt for credentials someone left on disk. A password for a local admin, a domain account, or a service sitting in a config file, a script, a history file, or a note turns "I can read files" into a higher-privileged context - or a domain foothold. This is the lowest-value, highest-effort lookup, so it comes last; but re-run it after every escalation, because SYSTEM can read files your foothold user couldn't.

Success indicator: a recovered cleartext password (or crackable hash / private key) you can reuse for a higher-privileged local or domain account - confirm with runas, WinRM, or an authenticated service logon.

When this applies

Credential hunting is the fallback, not the opener - a full file-system sweep is hours of work and the lowest hit-rate step in the loop (see the overview's operational sequence). Reach for it when:

  • Token privileges, group memberships, missing patches, and service/ACL audits have all come up empty.
  • You've just escalated and should re-sweep: SYSTEM or a new admin context can read profile paths, registry hives, and share folders your previous user couldn't. Always recheck PowerShell history and user profiles after gaining local admin.
  • You have a domain foothold and want to pivot: a password on a share or in a script is frequently the path from local access to a domain account.

Note

Enumeration scripts (winPEAS, Seatbelt, LaZagne) already search most of these locations, and you should run them - but understand the manual techniques too. Scripts miss non-standard files, get blocked by AV, and can't reason about which share folder is interesting. Manual hunting also lets you target a specific user's profile once you can read it.

Config files

Against best practice, applications routinely store passwords in cleartext config files. findstr is the workhorse for searching file contents recursively:

  • /S recurse subdirectories · /I case-insensitive · /M print only the filename · /C:"..." literal search string.
  • Drop /M to see the matching line (findstr /SI "password" *.config), add /N for line numbers, /P to skip binary files.

IIS stores credentials (connection strings, app-pool identities) in web.config. The default site's is at C:\inetpub\wwwroot\web.config, but there are often several across sites and application directories:

Network shares

In a domain, the richest hunting ground is file shares - user home folders with loose ACLs (every Domain User can read everyone's folder), departmental shares, backup locations. Snaffler crawls accessible shares and flags interesting files by extension and content:

It surfaces .kdbx (KeePass), .ppk (PuTTY key), .vmdk/.vhdx (virtual disks you can mount for the local SAM), .config, SSH private keys, and files whose names or contents look credential-bearing. A single password on a forgotten share is a common initial-access-or-escalation win.

Defense

  • Never store credentials in config files, scripts, or answer files; use a secrets manager or managed identities (gMSA) and reference secrets at runtime.
  • Delete unattend.xml/sysprep answer files after imaging, and scrub image-build shares. Audit C:\Windows\Panther\.
  • Tighten share ACLs - home folders should be readable only by their owner and admins, not all Domain Users. Run Snaffler yourself to find what an attacker would.
  • Disable PowerShell plaintext history for privileged automation, or keep secrets out of command lines (prompt, or read from a vault) so they never reach ConsoleHost_history.txt.
  • Monitor for mass file reads of profile/AppData paths and for findstr/Select-String sweeps across the file system.
